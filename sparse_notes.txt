Vector ownership and handle validity rules for the class matrix_s
    The operators call on MKL sparse functions. These functions return an opaque sparse_handle_t object from which we can extract the 3 CSR arrays. 
        mkl_sparse_?_create_csr creates a handle from the CSR form.
        mkl_sparse_?_export_csr exports the CSR vectors from the handle.
    The three CSR vectors are ALWAYS valid and must be kept so.
    For efficiency, handles are generated only when needed.
        As a result, matrices generated using the CSR constructor do not initially contain a handle.
        As a result, if any of the arrays is changed, the handle becomes invalid and is regenerated only before MKL calls.
    Vectors created by extracting the CSR form from a handle are still owned by MKL.
        They cannot be freed by us.
        They can be changed, but change will invalidate the handle.
    Thus, keeping track of array ownership is vital to avoid double-freeing the CSR arrays.
    Thus, keeping track of handle validity is vital to avoid unpredictable operation results.
    At the point of destruction:
        If the CSR vectors were generated by us, then they must be freed.
        If the CSR vectors were extracted from a handle we created, then they must be freed.
        If the CSR vectors were extracted from a handle created by an MKL call, then they must NOT be freed.
            e.g., when destroying an object produced by multiplying two matrices, we must not free the vectors, only the handle.
    Ownership of vectors and validity of handles is tracked by the two booleans.
